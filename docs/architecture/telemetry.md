# Compiler observability: SQLite run records and correlated signals

## Contract and boundaries

The compiler's human-facing diagnostics and help are independent of observability. They belong on stderr; telemetry never writes to stdout or stderr. A caller may render `RunSummary` to stderr after `finish_run`, but the library returns data only. An empty `TelemetryConfig::database_path` does not call SQLite or touch the filesystem. If `collect_summary` is also false, signal methods return immediately; the CLI should avoid creating unnecessary spans in this mode. Failure to open, migrate, or write the database never changes a compiler exit status. The caller can report `RunSummary::database_error` once if desired.

Each `Telemetry` instance represents one invocation and is single-use. Call `begin_run` before signals and `finish_run` after all `Span` objects have been destroyed and all worker tasks have joined. `Span` is movable and RAII-ended; it must not outlive its owner. The recorder serializes queue/SQLite access with a mutex, so producers can be concurrent. The caller passes `TraceContext` explicitly into worker tasks. This avoids incorrect implicit thread-local parentage when a task migrates threads. An empty parent denotes the invocation root. An imported `RunInfo::remote_parent` continues its trace if it has canonical lowercase, nonzero hexadecimal IDs of 32/16 characters; otherwise a fresh trace is created. Export `Span::context()` or `Telemetry::root_context()` to external workers. IDs are seeded from `std::random_device` once per thread and generated with a fast PRNG; they are correlation IDs, not secrets or authentication tokens.

## Schema and measurement

`run` stores invocation metadata, process ID, root and optional remote-parent span IDs, start epoch nanoseconds, monotonic duration, status, and escaped JSON attributes. `span` stores parent-child relationships, thread ID, start and duration, status, and attributes. `event`, `metric`, and `log` store timestamp, thread ID, trace/span IDs, attributes, and signal-specific fields. Integer epoch nanoseconds are for cross-process alignment; duration is measured with `steady_clock` so wall-clock adjustment cannot make elapsed time negative. Values in `Attributes` are UTF-8 text encoded as a JSON object, not raw SQL/JSON input. Metrics reject nonfinite values because SQLite maps NaN to SQL NULL, violating `metric.value NOT NULL`.

SQLite uses WAL for simultaneous readers and one writer, a bounded busy timeout, prepared statements, and batched transactions (default 128 signals). `run` is inserted at start and updated at finish; the root span is inserted on finish. A crash may therefore leave a `running` row and lose the final partial batch. This is deliberate: the database is observability, not an audit ledger. Failed writes disable persistence for the rest of the invocation, while in-memory summary counts continue. Small compilations with no `--db` avoid connection setup, schema checks, journaling, and transactions entirely. Summary-only mode counts signals without JSON serialization or database access.

`RunSummary::database_setup_duration` is timed by `steady_clock` only when a database path is configured. Its interval starts immediately before `open_db()` and ends after the attempted initial `run` insert, including SQLite connection creation, busy timeout, WAL and foreign-key PRAGMAs, `CREATE TABLE`/index checks, statement preparation, and the insert. `RunSummary::database_finish_duration` starts before enqueueing the root span in `finish_run` and ends after the attempted final batch flush and `run` status update. If setup failed, finish performs no batch or update and this field stays zero. `RunSummary::database_close_duration` starts immediately before prepared-statement finalization and ends after `sqlite3_close`; it is zero if no SQLite handle exists. `finish_run` performs this close before returning its summary, and the destructor safely closes an unfinished run. Repeat `finish_run` calls preserve the first summary and never double-close. All three fields stay zero when no database path is configured. They exclude signal batches flushed earlier during compilation, identifier creation, mutex wait, and CLI formatting. A WAL auto-checkpoint triggered by a commit belongs to setup/finish as appropriate; a final checkpoint triggered by connection close belongs to close. The main `duration` is sampled **before** final flush and close, so it describes the invocation up to compiler completion rather than the full telemetry-export lifetime. The component intervals are not a full accounting identity for wall-clock process lifetime.

The SQLite database should be a local filesystem path: WAL's shared-memory coordination is not suitable for a network filesystem. This is an implementation of OpenTelemetry-style trace/span correlation, **not** an OTLP exporter or a promise of wire-level OTel compatibility. The schema has no automatic retention, redaction, or multi-process migration policy yet. CLI integration should avoid recording full source text, secrets, or unrestricted command lines in attributes; paths and diagnostic messages may themselves be sensitive. A future schema change needs explicit versioned migration before altering established columns.

## Evidence and operational checks

- `tests/telemetry_test.cpp` checks disabled mode, actual SQLite persistence for all five tables, parent IDs, JSON validity, concurrent worker records, and database-open failure isolation. The local direct build command is `g++ -std=c++23 -I include src/telemetry.cpp tests/telemetry_test.cpp -lsqlite3 -o .cache/telemetry_test.exe`, then run it from the repository root. The test database stays in `.temp/`.
- SQLite documents that WAL permits readers during a writer commit but still has one writer at a time and should not be used over a network filesystem: [SQLite WAL](https://www.sqlite.org/wal.html). Its [busy-timeout API](https://sqlite.org/c3ref/busy_timeout.html) bounds lock waiting.
- OpenTelemetry defines a trace ID shared across spans and parent span IDs for causal relationships: [OTel specification overview](https://opentelemetry.io/docs/specs/otel/overview/). The current explicit context API is designed around that model rather than ambient thread-local state.

## Open design risks

1. A single mutex can contend if fine-grained events are emitted at high volume from many worker threads. Before adding a lock-free queue, benchmark realistic compilation traces and compare event batching or sampling. For the expected phase-level instrumentation, simplicity should win.
2. A crash can leave a `running` row; any dashboard must represent that as incomplete, not successful or necessarily failed.
3. IDs are probabilistically unique and not cryptographic. If traces cross hostile trust boundaries, an authenticated propagation format and privacy policy are needed.
4. The schema is intentionally compact. If later task-graph edges need multiple causal parents, add a separate span-link table rather than overloading `parent_span_id`.
