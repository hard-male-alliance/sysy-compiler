# 2026-09-27 compile-time baseline (provisional)

## Reproducibility and environment

**Decision purpose:** establish whether small-file startup or a large source is limited by front-end/back-end work, and quantify optional SQLite/tracing cost before proposing any production optimization. No production optimization was made from these results. The tested Windows Release binary SHA-256 begins `ad227d596c398db4`; full hash, generated input hash, every raw timing, and command are in the JSON files below. This is a **single host and one build**, not a cross-machine performance claim.

| Item | Value |
| --- | --- |
| Host | Windows 11 build 26200; Intel Family 6 Model 154 Stepping 3, x86-64; Python 3.14.6; MinGW Release build `.cache/build/release/compiler.exe` |
| WSL exploratory host | WSL2 Ubuntu 24.04, Linux 6.18.33.2-microsoft-standard-WSL2; GCC 13.3.0 Release binary in `.cache/build/wsl-release/compiler`, SHA-256 begins `c542f7f8069e51bd`; all files on `/mnt/d` (DrvFS/NTFS), **not** native ext4 |
| Timing | Python `perf_counter_ns` around fresh process start-to-exit; output streams to `DEVNULL`, except `summary_probe.py`; 3 warm-ups + 31 measured samples for regular Windows cases; 2 + 15 for large cases |
| Inputs | UTF-8 with LF bytes in final Windows/WSL baselines; `tiny` 25 B; medium `functions` 31,980 B (120 functions × 16 statements); large `functions` 190,220 B (400 × 32); `arrays` is a sparse source with a large global array |
| Outputs | All measurements under `.temp/performance/`; no system-wide cache flush, affinity, Defender exclusion, or CPU governor control |

Exact commands (from repository root; `.exe` on Windows):


WSL exploratory command (run from the repository root **inside WSL**): `python3 benchmarks/compile_time.py --compiler .cache/build/wsl-release/compiler --repetitions 15 --warmups 2 --functions 120 --statements 16 --out .temp/performance/wsl_off_lf`, after `cmake -S . -B .cache/build/wsl-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF && cmake --build .cache/build/wsl-release --parallel 4`. The build and benchmark live on a DrvFS-mounted Windows volume; results must not be labeled native Linux.

## Observations

| Windows Release workload | Default/no DB median [bootstrap 95% CI] | p95 | SQLite paired overhead median [bootstrap 95% CI] |
| --- | ---: | ---: | ---: |
| `compiler --version` control | 13.51 ms (not a compilation) | — | — |
| Tiny 25 B | 16.02 ms [15.70, 16.39] | 21.25 ms | +12.31 ms [11.6, 13.2] |
| 120-function 31,980 B | 24.99 ms [24.46, 25.78] | 29.35 ms | +18.13 ms [16.1, 19.7] |
| Array source 549 B | 16.10 ms [15.47, 16.76] | 19.62 ms | +14.64 ms [13.5, 18.5] |

The **no-database** `--summary` probe reports a median in-process `total` of **1.79 ms** [1.74, 1.85] for the tiny file. Its shown stages were `publish` 1.43 ms, `codegen` 0.04 ms, `semantic` 0.03 ms, `parse` 0.03 ms; the two remaining stages were too small to appear in the top-four human summary. This supports the inference that process load and other uninstrumented fixed costs dominate the default tiny-file end-to-end latency. Do **not** subtract 1.79 ms from the separate 16.02 ms experiment and call the remainder “startup”: the clocks have different boundaries and runs, and summary capture uses a pipe.

The interleaved `--summary` versus default comparison (31 AB/BA pairs, an earlier CRLF-generated source revision) showed median deltas tiny **−0.01 ms** [−2.68, +1.44], functions **+1.65 ms** [−2.50, +2.55], arrays **+0.06 ms** [−0.71, +1.59]. Thus no detectable summary-only overhead at this sample size; the material +12–18 ms treatment is associated with SQLite persistence, not merely in-memory stage timing. The older CRLF report is retained at `.temp/performance/paired_summary/results.json` for audit and should not be combined numerically with LF workload hashes.

For the **large 190,220 B source** at `-O0`, 15 telemetry runs gave these **median span times**: `codegen` 17.69 ms, `parse` 13.80 ms, `lower` 11.83 ms, `semantic` 10.15 ms, `publish` 3.29 ms, `optimize` 0.93 ms. The external telemetry-on median was 101.16 ms [99.99, 103.93]. These spans are single-run stages and approximately serial here, but they do not cover input load, telemetry DB open/flush, or process startup. Code generation is the largest **instrumented** stage, not necessarily the largest end-to-end cost. A separate interleaved `-O0`/`-O2` comparison without DB (15 pairs) measured large-source medians 87.42 versus 89.67 ms, paired difference **+2.49 ms** [−1.99, +3.73]; this is inconclusive. `-O2` assembly was 2,437,522 B versus `-O0` 2,771,150 B (12.0% smaller), but output size alone says nothing about runtime performance or semantic equivalence.

WSL2 on `/mnt/d` produced default medians `--version` 4.15 ms, tiny 19.67 ms, medium functions 30.23 ms, arrays 21.75 ms (15 measured samples). A previous WSL pass on the same mount reported tiny 53.14 ms, illustrating strong mount/host-state variability. Do not compare WSL and Windows numbers as operating-system performance rankings. Native Linux filesystems and independent CI runners remain unmeasured.

## Interpretation, risks, and next decision

1. **Observed:** default tiny compilation is in the 15–20 ms range in the lower-noise Windows runs; the compiler's reported in-process work is ~2 ms. **Inference:** optimizing the parser or IR cannot materially improve this workload before fixed process/IO costs are addressed. The `--version` control is consistent with this, but not a causal decomposition.
2. **Observed:** SQLite-on paired cost is large relative to a tiny compile, while summary-only cost is below this experiment's resolution. **Hypothesis:** DB open/journal setup, per-run transaction/flush, or filesystem/Windows Defender activity dominate; current trace spans do not bracket DB open/flush. One earlier telemetry array run spent 3,085 ms inside `run.duration` but <6 ms across named compiler stages, and 3,764 ms externally. This supports an uninstrumented stall, **not** proof that SQLite alone or Defender caused it. Instrument DB lifecycle separately before attempting a fix; keep DB opt-in meanwhile.
3. **Observed:** with 400 functions/32 statements, codegen is the largest measured compiler stage (~17.7 ms), followed by parse/lower/semantic. **Recommendation:** if long-source latency becomes a decision priority, profile codegen's instruction formatting/allocation first and validate against end-to-end time and assembly correctness. Its theoretical best-case headroom from a 2× stage speedup is <9 ms, not a whole-program 2× speedup. The current `-O0`/`-O2` latency difference is not established as a regression.
4. **Measurement risk:** this is a concurrently used Windows machine; CPU scheduling, frequency, antivirus scanning and NTFS/DrvFS filesystem behavior were not controlled. Earlier paired SQLite runs showed +18–23 ms median and a multi-second tail, whereas the lower-noise LF series showed +12–18 ms. AB/BA pairing limits slow drift but not per-process outliers or filesystem interference. Replicate on a quiet native Linux CI runner before setting numeric performance gates or accepting an optimization.

The methodology follows [LLVM benchmarking guidance](https://llvm.org/docs/Benchmarking.html) and the project-local [methodology note](compile-time-methodology.md). The research motivation for stage/outlier analysis is [Huemer et al., ECOOP 2024](https://doi.org/10.4230/LIPIcs.ECOOP.2024.20); their JIT results do not transfer quantitatively to this compiler.

## Follow-up: SQLite lifecycle attribution after close timing landed

This is a **new, isolated Windows Release build** in `.cache/build/perf-release/compiler.exe`, SHA-256 `62042825984f324de4567d2042efb68c9588b00a16076cfc146c07febc515426`. It is not numerically pooled with the earlier binary. The new CLI summary reports `elapsed` (in-process run duration plus measured finish/close), and separate `setup`, `flush`, `close` durations. The measurement source uses a previously created local SQLite database after three warm-up runs; first-time schema creation may cost more. Source bytes are LF-normalized. Build command: `cmake -S . -B .cache/build/perf-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF; cmake --build .cache/build/perf-release --parallel 4` with MinGW GCC 16.1.0 and SQLite 3.53.1.

Exact commands:

```powershell
python benchmarks/telemetry_pair.py --compiler .cache/build/perf-release/compiler.exe --repetitions 31 --warmups 3 --functions 120 --statements 16 --treatment db --out .temp/performance/perf3_paired_db
python benchmarks/summary_probe.py --compiler .cache/build/perf-release/compiler.exe --repetitions 31 --warmups 3 --case tiny --db --out .temp/performance/perf3_tiny_lifecycle
python benchmarks/summary_probe.py --compiler .cache/build/perf-release/compiler.exe --repetitions 31 --warmups 3 --case functions --functions 120 --statements 16 --db --out .temp/performance/perf3_medium_lifecycle
python benchmarks/summary_probe.py --compiler .cache/build/perf-release/compiler.exe --repetitions 31 --warmups 3 --case tiny --out .temp/performance/perf3_tiny_no_db
python benchmarks/summary_probe.py --compiler .cache/build/perf-release/compiler.exe --repetitions 31 --warmups 3 --case functions --functions 120 --statements 16 --out .temp/performance/perf3_medium_no_db
```

| Workload | Paired external no-DB median | DB median | Paired DB addition, median [bootstrap 95% CI] | DB `setup` | DB `flush` | DB `close` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Tiny 25 B | 16.70 ms | 36.18 ms | +20.00 ms [18.36, 21.19] | 7.06 ms | 3.63 ms | 4.86 ms |
| Functions 31,980 B | 27.80 ms | 52.55 ms | +24.00 ms [22.90, 24.57] | 6.28 ms | 3.40 ms | 4.94 ms |

The lifecycle columns are medians from **separate** 31-run `--summary --db` diagnostic series; they are not subtractions from each row's paired external median. The median *per-invocation* sum of setup+flush+close was 16.70 ms for tiny and 15.56 ms for functions. `setup` is the largest **single** measured SQLite step, but `close` is also material and `flush` is not negligible: no single step explains the entire DB treatment. For tiny, the lifecycle sum was a median 92.6% of the compiler's reported DB-mode `elapsed` (18.06 ms median). For functions, it was 57.0% of reported `elapsed` (27.61 ms median). The no-DB `elapsed` medians in parallel diagnostic runs were 1.20 ms and 12.15 ms respectively. These internal values have different time boundaries from the external process metric and came from captured-stderr runs, so their differences do not close an accounting identity with the paired treatment.

**Judgment:** SQLite open/schema/run insertion and finalization/close are jointly the first measured optimization target if opt-in telemetry latency matters. A production change cannot be justified yet: on Windows/NTFS, OS cache state, filesystem sync, antivirus scanning, and concurrent workload may change the balance. In particular, a medium-source setup sample reached 184.66 ms while its median was 6.28 ms. A useful next experiment would split `setup` into open/PRAGMA/schema/insert and `close` into statement finalization/connection close, then repeat on a quiet native Linux filesystem and Windows; it would change whether to consider connection management or SQL transaction structure. Keep SQLite disabled by default and preserve durability/trace correctness over speculative speedups.

The subsequent [SQLite lifecycle microbenchmark](sqlite-lifecycle-microbenchmark.md) specifically compared WAL versus rollback journal and repeated DDL versus a `user_version` fast path. Neither proposed production change was supported for this short-lived Windows workload; its results narrow the options but do not replace a compiler-level measurement.
