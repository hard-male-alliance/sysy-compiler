# Follow-up branch compile-time regression check (2026-09-27)

## Decision and provenance

Decision question: did the follow-up implementation snapshot for prototypes, `mem2reg`, lowering and the RISC-V backend introduce a **material (>10%)** regression in common small or moderately large `-O0`/`-O2` compilations relative to commit `bbafefc`? This is a bounded compile-time check, not a claim about target-program runtime or full SysY workload coverage.

The existing `.cache/build/release/compiler.exe` was **not used as baseline**. Its SHA-256 began `ad227d…` and timestamp preceded commit `bbafefc`; a compatible source provenance could not be established. Instead, `git archive bbafefc` was extracted under `.temp/performance/followup_regression/baseline_src` and built into `.cache/build/perf-bbafefc`. Current `CMakeLists.txt`, `src/`, and `include/` were snapshotted into `.temp/performance/followup_regression/followup_src` and built into `.cache/build/perf-followup`. The follow-up snapshot's 20-file SHA-256 manifest is `.temp/performance/followup_regression/followup-source-manifest.json`, tree digest `acd82ff4ff35553437e295dd21ff71366e4b2ba6d77b7bdbb0b3587294ed71b0`. This is a fixed **working-tree snapshot**, not a named follow-up commit; later edits to the branch are outside this comparison.

| Binary | SHA-256 |
| --- | --- |
| Exact `bbafefc` baseline | `5d91166614cb30db937ebda2ffb7b6e230690fb547654e96658656b2144be143` |
| Follow-up snapshot | `e4603281897fe682d7a145fdf2fc933fc0cd2544a1bf6c98a45aec01928b81a5` |

Both isolated CMake Release builds used MinGW GCC 16.1.0 and SQLite 3.53.1 on Windows 11 build 26200, with `-O3 -DNDEBUG -std=c++23` in the build rules, `BUILD_TESTING=OFF`, and no sanitizer or target runtime. Python 3.14.6 ran the benchmark. All sources, binaries, inputs and outputs remained under repository `.temp` or `.cache`.

Reproduction after recreating the two source snapshots described above:

```powershell
cmake -S .temp/performance/followup_regression/baseline_src -B .cache/build/perf-bbafefc -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build .cache/build/perf-bbafefc --parallel 4
cmake -S .temp/performance/followup_regression/followup_src -B .cache/build/perf-followup -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build .cache/build/perf-followup --parallel 4
python benchmarks/compiler_pair.py --baseline .cache/build/perf-bbafefc/compiler.exe --candidate .cache/build/perf-followup/compiler.exe --repetitions 31 --warmups 3 --functions 120 --statements 16 --out .temp/performance/followup_regression/paired_1
python benchmarks/compiler_pair.py --baseline .cache/build/perf-bbafefc/compiler.exe --candidate .cache/build/perf-followup/compiler.exe --repetitions 31 --warmups 3 --functions 120 --statements 16 --out .temp/performance/followup_regression/paired_2
```

The runner generated byte-identical LF SysY inputs for both binaries: tiny 25 B (`deac66ccb79f6d31c0fa…` SHA-256) and 120-function/16-statement 31,980 B (`263328a6bdc4ad337faa…`). Within every case and `-O` level, both compilers read the **same source path** and overwrite the **same assembly output path**. Each sample starts a fresh process with stdout/stderr redirected to `DEVNULL`; the baseline/candidate order alternates AB/BA for each of 31 measured pairs after three warm-ups. The JSON reports retain every latency, complete command, hashes and bootstrap interval. Neither database telemetry nor human summary was enabled.

## Results

Medians in milliseconds; paired delta is follow-up minus baseline, with a 95% seeded bootstrap interval for the median. Replicates are reported separately rather than pooled across time:

| Workload | Replicate | Baseline | Follow-up | Paired delta [95% interval] | 10% threshold from baseline |
| --- | ---: | ---: | ---: | ---: | ---: |
| Tiny `-O0` | 1 | 15.74 | 15.32 | −0.56 [−0.94, +0.06] | 1.57 |
| Tiny `-O0` | 2 | 15.70 | 15.31 | −0.55 [−0.75, −0.10] | 1.57 |
| Tiny `-O2` | 1 | 15.71 | 15.62 | +0.07 [−0.42, +0.29] | 1.57 |
| Tiny `-O2` | 2 | 15.92 | 15.46 | −0.16 [−0.42, +0.43] | 1.59 |
| 120 functions `-O0` | 1 | 27.35 | 28.22 | +0.70 [+0.08, +1.21] | 2.74 |
| 120 functions `-O0` | 2 | 27.88 | 27.74 | +0.11 [−0.86, +1.12] | 2.79 |
| 120 functions `-O2` | 1 | 29.49 | 29.61 | +0.04 [−0.56, +1.20] | 2.95 |
| 120 functions `-O2` | 2 | 28.48 | 28.41 | +0.21 [−0.73, +0.71] | 2.85 |

**Observation:** every case compiled successfully. No paired median or 95% upper interval approached the predeclared 10% material-regression threshold. Tiny `-O0` appears slightly faster and the first 120-function `-O0` replicate slightly slower, but those are sub-millisecond effects on this host; the latter did not recur in replicate 2. Treat them as inconclusive for an optimization decision, not as proven changes to compiler speed.

**Boundary:** this suite does not include very large arrays, worst-case CFGs, telemetry-enabled runs, output validation, or target execution. It can rule out a large regression for the two measured workload shapes, not for every SysY program. Windows scheduling, frequency scaling, antivirus and filesystem state remain uncontrolled; AB/BA pairing limits slow drift, not arbitrary per-process noise. A future regression decision should use representative real sources and a quiet native Linux runner in addition to this Windows check.
